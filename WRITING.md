# Writing standard

I use these rules for project READMEs and public copy. They come from ASD-STE100 and from DHH's habit of saying the plain thing first.

1. Write one idea per sentence. Keep sentences short.
2. Use active voice. Say who did what.
3. Use the exact technical name. Say PBKDF2, not "secure hashing".
4. Call a demo a demo. Name the sandbox, the sample data, and the missing backend.
5. Do not use hype words. Remove "amazing", "seamless", "robust", and "production-ready" unless the code proves them.
6. Do not use slang. Remove "legit", "stuff", and "basically".
7. State what the system does when input is wrong. Errors are part of the feature.
8. Verify every link and every number before publishing it.
9. If I cannot verify a claim, I remove the claim.

When I edit an old document, I apply these rules to the lines I touch.
